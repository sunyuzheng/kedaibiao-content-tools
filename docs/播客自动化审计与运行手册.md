## 审计中发现的主要风险

旧流程有这些系统性问题：

1. 定时任务跑未纳入版本控制的脚本；现役和归档入口容易混淆。
2. 候选只扫描 `archive/有人工字幕`，并把历史物理目录误当业务状态。
3. 只获取 published episodes；已经创建的 draft 在重跑时可能再次创建。
4. 读取了 SRT，但 create payload 没发送 transcript。
5. create 成功、publish 失败时仍返回成功。
6. dry-run 和正式运行各自重新发现候选，没有同一个不可变执行计划。
7. YouTube privacy snapshot 过期后仍可参与发布判断。
8. `--ignore-errors` 把 yt-dlp 的真实失败一起吞掉。
9. 质量检查把“视频真实发布日期恰好是今天”误报为错误。
10. 重排遇到缺失日期或 API 限流时可能留下半完成状态。
11. launchd `StartInterval` 在笔记本休眠期间可能错过，且使用系统 Python。
12. 日志只是一大段文本，无 heartbeat、审批记录、结构化 ledger 或保留策略。
13. `.env`、OAuth token 和 client secret 的本地权限过宽。

## 新的数据流

```text
匿名频道清单（≤72h）+ 下载归档 / 已知会员 deny set
          │
只下载未见过的增量条目 + info.json + 本地 SRT/VTT
          │
canonical local records + Transistor 全量快照
          │
候选发现 plan → 仅对 publish candidates 做低频 yt-dlp 验证
          │
最终 immutable sync-plan.json + latest.md
          │
精确审核 scope / targets / source hashes / approval hash
          │
apply_transcripts 或 prepare_and_publish
          │
逐条远端回读 + JSONL ledger
          │
quality plan / reorder plan
```

`video_id` 是跨本地和 Transistor 的幂等键。remote absent、单 draft、多 draft、
published 分别处理；执行期状态与计划不符时停止，不临场猜测。

匿名 `/videos` 清单只能用于发现，因为 YouTube 会把会员 teaser 也展示在列表中。
下载队列由当前清单减去 download archive、本地已知 member-only info 和持久化 deny set
得到，所以正常情况下每天只访问新增条目。计划生成后，再只对本次 publication
candidates 做带 request sleep 的 yt-dlp 可访问性验证；未验证、限流或权限错误都进入
blocked，不能发布。OAuth 全量快照仅用于补充 unlisted/private 审计；token 失效不会
放宽发布条件。清单或候选验证证据超过 72 小时时，发布 fail-closed。

## SRT/VTT 处理

Transistor 的公开 API 支持 `episode[transcript_text]`，不提供上传原始 SRT 文件的公开
字段。当前实现会：

1. 确定性选择最高优先级 timed transcript。
2. 去除 cue 编号、时间戳和 VTT 标签，保留全文。
3. 在计划中记录来源路径、source status、字符数和 SHA-256。
4. 执行前重新计算 hash。
5. PATCH 后检查 `transcript_text`（若 API 回传）或 `transcript_url` /
   `transcripts` artifact（公开 API 的常见响应）。
6. 远端已有 transcript、但 API 不能回读原文比较时不自动覆盖。

原始 SRT/VTT 和时间戳仍以本地 archive 为 source of truth。

## 审批边界

每周日 09:15 的定时任务永远 plan-only。以下操作都属于远端内容变更，必须分别审核并批准对应 hash：

- 482 个现有 episode 的 transcript backfill
- 新 episode 的 draft 修复/创建与公开发布
- 全量 episode number/title 重排

计划被编辑、本地文件 hash 改变、YouTube snapshot 过期、show id 改变或远端前置状态
改变时，执行器都会拒绝继续。ledger 是执行历史，不替代远端状态或 canonical manifest。

定时任务访问 YouTube 前会用项目 Python 向 PyPI 检查 yt-dlp stable/nightly，并尝试安装
最新 pre-release。升级结果和前后版本写入结构化日志；网络、索引或升级失败时，只要
现有项目 yt-dlp 仍可执行就降级为 warning 并继续。锁定的 requirements 版本仍是
新环境的已知良好基线，不代表周任务长期停留在该版本。

如 `.env` 同时配置 `RESEND_API_KEY`、`RESEND_FROM_EMAIL` 和
`PODCAST_SYNC_EMAIL_TO`，每次周任务会发送一封摘要邮件。请求使用
`Idempotency-Key` 避免同一次运行因网络重试重复发信；发送失败会写入 JSONL 日志，
但不会改变同步任务的成功/失败判定。未配置或只配置一部分时不发送，并在日志记录
`not_configured` 或 `incomplete_configuration`。

2026-07-27 已验证这条更新路径将项目 yt-dlp 从 `2026.07.04` 升级为
`2026.07.23.234303` nightly；更新器在无法联网升级、但旧版本仍可执行时返回可审计的
warning，只有项目内没有可运行版本时才令周任务失败。

## 对参考指南的采用与修正

参考指南中值得保留的原则：

- 文件响应模式：本流程使用不可变 JSON plan 和人类可读 Markdown summary。
- JSONL 流式日志：scheduler 和远端执行器均实时输出结构化事件。
- 超时与失败必须显式：所有网络调用有 connect/read timeout、有限重试和非零退出码。
- 产物要验证：本地 source hash、远端 precondition 和写后 readback 都参与验证。

对 Codex CLI 的当前修正：

- 新自动化如需要 Codex，应使用 `codex exec`。
- 默认使用 read-only sandbox；确实需要文件修改时显式
  `--sandbox workspace-write`。
- `--full-auto` 是兼容参数，不应写入新脚本。
- 机器消费使用 `--json` JSONL；最终结构化产物使用 `--output-schema` 和
  `--output-last-message`。
- 不在 deterministic 上传路径中加入 AI。AI 可用于 show notes、标题建议或质量报告，
  但产物必须先进入本地文件和 schema 校验，不能绕过 approval hash 直接发布。
